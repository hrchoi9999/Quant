Harness Performance Research Governance Design

기준일 2026-07-10 · 대상: Quant 전략모델, AI 학습모델, QuantAnalysis 포트폴리오 구성
결론: 업데이트 파이프라인에 연구 단계를 계속 추가하지 않는다. 하네스에 별도 Performance Research Campaign을 두고, 한 캠페인에서 하나의 baseline, 하나의 후보, 하나의 동결된 가설만 검증한다. 하네스는 연구 설계와 증거 게이트를 책임지고, Quant Model과 QuantAnalysis는 각자 소유한 로직의 실험을 수행하며, 사용자는 운영 반영을 승인한다.

1. 현재 구조에서 확인된 핵심 문제

문제영향설계 보정
성과 거버넌스가 후보 목록만 만들고 실험 조건을 잠그지 않음대상 스레드가 baseline 정리, 후보 탐색, 검증을 동시에 수행해 범위가 넓어짐작업지시 전에 하네스가 experiment contract를 생성
기존 모델 간 비교와 신규 개선 실험이 혼재S6 → S5처럼 과거 우열이 실제 개선 성과처럼 보임historical_comparison과 frozen_improvement_experiment를 별도 상태로 관리
보유기간과 실행가격 정의가 불완전QuantAnalysis의 기존 -15.278%처럼 서로 다른 보유기간이 혼합됨공개 후 다음 거래일 시가 진입, 5번째 거래일 종가 청산을 기본 계약으로 고정
OOS를 본 뒤 좋은 규칙을 선택relative_gate의 개선이 사후선택 편향을 가짐후보 규칙을 먼저 동결하고 새로운 OOS만 평가
중첩 에피소드로 복리수익과 MDD를 계산투자 가능한 NAV보다 과장되거나 왜곡된 위험 지표 생성중첩 수익률은 paired outcome에만 사용하고 MDD는 비중첩 NAV로 계산
승인 기준과 중단 조건이 정량화되지 않음결과가 매번 provisional로 끝나고 다음 행동이 불명확함owner별 최소 표본, 비용, MDD, turnover, 신뢰구간 gate 고정

2. 운영 파이프라인과 연구 캠페인의 분리

영역역할금지
주중 WD04/WD05freshness, current 성능 이상, 모델/포트폴리오 열화 후보 탐지장기 연구, 후보 자동 선택, 정책 변경
주말 WE01Quant Model만 실행하여 기존 research_full과 모델·AI 후보 우선순위 갱신QuantAnalysis 실행, public publish, 자동 정책 반영
Performance Research Campaign하네스가 사전 조사 후 한 개의 동결 실험을 owner 스레드에 지시주중/주말 update cycle과 동시 heavy execution, 여러 후보 동시 탐색
주말 하네스가 Quant Model 전용이라는 기존 원칙은 유지한다. QuantAnalysis 성능 연구는 주말 update cycle에 넣지 않고, 별도 승인된 연구 캠페인으로 실행한다.

4. 증거 등급과 승격 규칙

등급의미허용 판단
E0 diagnostic현재 상태, 상관관계, 단순 성과 차이문제 제기만 가능
E1 comparable backtest동일 기간·유니버스·비용·리밸런싱의 과거 비교실험 후보 등록 가능, 운영 반영 불가
E2 frozen OOS/WF규칙 동결 후 독립 temporal OOS 또는 walk-forward 통과shadow 후보 가능
E3 shadow/live실제 공개 시점 이후 충분한 독립 표본에서 guardrail 통과사용자 승인 요청 가능
E4 approved operatingQuant Model 또는 QuantAnalysis owner 판단과 사용자 승인 완료운영 반영 가능
E5 post-change validated운영 반영 후 성과와 위험이 사전 계약 범위 안에 유지유지·확대 검토 가능

등급을 건너뛸 수 없다. 특히 E1의 큰 누적수익률 차이는 E2/E3를 대체하지 않는다.

5. KPI와 최소 증거 게이트

5.1 전략모델·ETF·Router

구분정의
Primary KPI비용 차감 OOS 순수익 또는 CAGR 개선폭, approved baseline 대비 excess return
GuardrailNAV MDD, Sharpe, turnover, 비용 민감도, 국면별 안정성, 단일 기간 수익 집중도
기본 최소 표본월간 ETF/E-series는 24 priced periods, 주간/종목 모델은 52 rebalance windows. owner가 freeze 전에 더 엄격한 기준을 지정할 수 있음
승격 추가조건2회 이상 주말 검증에서 동일 결론, 비용·MDD·turnover trade-off 공개, 사용자 승인

5.2 AI 학습모델·overlay

구분정의
Primary KPIAUC/IC가 아니라 AI 적용 후 전략의 비용 차감 수익, downside 회피, ranking 개선 기여도
표본 판정30+ live events는 high, 10~29는 provisional, 10 미만은 insufficient
FreshnessA operating core는 target asof 최신이 원칙. 3~5 거래일 초과 stale은 refresh 판단이 필요하며 stale waiver 없이는 운영 입력으로 사용 금지
Guardrail모델별·국면별 오탐, coverage, calibration, turnover 증가, stale feature 사용 여부

5.3 QuantAnalysis top3와 전체 포트폴리오

구분동결 정의
Canonical signal실제 GCS history에 공개된 포트폴리오 신호. latest 덮어쓰기 파일은 성과 원천으로 사용하지 않음
진입·청산공개 신호 이후 다음 거래일 시가 진입 → 진입일부터 5번째 거래일 종가 청산
Primary KPIbaseline top3 대비 paired 5거래일 순수익 개선폭과 benchmark-relative 개선폭
최소 표본신규 OOS 진입일 60일, top3 관측 180건, 비중첩 cohort 12개
Regime coverage시장등급 1~3과 4~5 각각 최소 20일
통계 gate주 단위 block bootstrap 95% CI 하한 > 0, paired median ≥ 0
품질 gatebenchmark-relative ≥ 0, top3 − rank4~10 > 0
위험 gate비중첩 NAV MDD 악화 없음, turnover 증가 ≤ 10%p, one-way turnover 비용 10bp

6. 실험 계약에서 반드시 잠글 항목

  1. Question: 어떤 운영 결정을 바꾸기 위한 실험인지 한 문장으로 정의한다.
  2. Owner: Quant Model 또는 QuantAnalysis 중 하나만 지정한다.
  3. Baseline: 이름, version, 데이터 snapshot/hash, 생성 시점을 기록한다.
  4. Candidate: 규칙과 파라미터를 완전하게 고정하고 실행 후 변경을 금지한다.
  5. Population: universe, eligibility, 결측·거래정지·상장폐지 처리 규칙을 잠근다.
  6. Timing: 신호 공개 시각, 진입·청산 시점, timezone, hold horizon을 잠근다.
  7. Comparison: benchmark, 비용, turnover, rebalance, risk budget을 동일하게 만든다.
  8. Split: train/validation/OOS/holdout 날짜를 사전에 기록하고 OOS 재선택을 금지한다.
  9. Metrics: primary 1~2개, driver 1~2개, guardrail 2~4개만 사용한다.
  10. Decision: pass/fail/insufficient 조건과 rollback 조건을 실행 전에 확정한다.

10. 표준 산출물과 등록부

구현 시 다음 경로를 사용한다. 이번 설계 단계에서는 아직 생성하지 않는다.

  • config/harness/performance_research_registry.yaml
  • reports/harness_performance_research/<campaign_id>/preflight.json
  • reports/harness_performance_research/<campaign_id>/experiment_contract.yaml
  • reports/harness_performance_research/<campaign_id>/owner_result.json
  • reports/harness_performance_research/<campaign_id>/evidence_gate.json
  • reports/harness_performance_research/<campaign_id>/decision_packet.html

등록부 필수 필드는 campaign_id, owner, status, baseline, candidate, frozen_rule, source_snapshot, split, execution_timing, cost, metrics, gates, evidence_level, approval, rollback이다.

11. 작업지시 품질 게이트

아래 항목이 하나라도 없으면 대상 스레드에 prompt를 보내지 않는다.

  • 단일 질문과 단일 owner
  • canonical baseline과 authoritative source
  • 완전히 동결된 후보 규칙
  • 신호·진입·청산 시점
  • 동일 universe, benchmark, 비용, rebalance
  • 독립 OOS/holdout 범위
  • primary KPI와 guardrail
  • 최소 표본과 pass/fail/insufficient 조건
  • 허용 파일과 금지 행동
  • 정책 변경·publish·자동매매 금지 또는 별도 승인

12. 제한사항과 해결 순서

  1. analysis.db에는 GCS publish 성공과 object hash가 없으므로 실제 공개 신호와 별도 대조가 필요하다.
  2. 과거 QuantAnalysis 저장 범위가 top10이라 top101 전체 대체 후보는 과거 재검증할 수 없다.
  3. AI-GROWTH는 2026-05-12 기준 stale이므로 최신 core 근거로 사용할 수 없다.
  4. 현재 governance 스크립트의 단순 score 임계값은 후보 탐지용이며 승인 게이트로 사용하지 않는다.
  5. 기존 dirty 12개와 untracked harness 파일은 이번 설계와 분리하고 되돌리지 않는다.

13. 구현 권고 순서

  1. 등록부와 contract schema: active campaign 하나와 증거 등급을 저장한다.
  2. preflight builder: source freshness, model scope, 이전 실험, baseline 적합성을 자동 점검한다.
  3. prompt renderer: contract가 통과한 경우에만 owner prompt를 생성한다.
  4. evidence gate: owner 결과를 재계산하고 insufficient/provisional/approval_eligible을 판정한다.
  5. update cycle 연결: WD04/WD05/WE01은 후보를 등록할 뿐 연구를 직접 실행하지 않는다.
  6. 첫 캠페인: E-series holdout과 relative_gate frozen shadow를 각각 owner 단위로 시작한다.
